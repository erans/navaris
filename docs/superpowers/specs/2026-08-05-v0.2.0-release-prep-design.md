# v0.2.0 Release Preparation Design

## Goal

Align the Claude Code plugin metadata with the upcoming Navaris `v0.2.0` release before creating the release tag.

## Current State

Navaris `main` is ready for the next release and uses Go 1.26.5. The documented plugin versioning policy says the Claude Code plugin version moves with Navaris CLI release tags, but both plugin manifests still declare `0.1.0`:

- `.claude-plugin/plugin.json`
- `.claude-plugin/marketplace.json`

Creating `v0.2.0` without updating these manifests would make the tagged source inconsistent with that policy.

## Design

1. Change the top-level `version` field in `.claude-plugin/plugin.json` from `0.1.0` to `0.2.0`.
2. Change the plugin entry's `version` field in `.claude-plugin/marketplace.json` from `0.1.0` to `0.2.0`.
3. Do not alter names, descriptions, sources, skills, application code, dependencies, release workflows, or other version examples.
4. Validate both files as JSON and assert that both declared plugin versions are exactly `0.2.0`.
5. Deliver the metadata change through a pull request and require green CI before squash-merging it.
6. Create the `v0.2.0` release tag only after the preparation PR is merged and its merge commit is present on `origin/main`.

This manual two-file bump is preferred over adding version-derivation automation during release preparation. Automation would expand the release scope and can be designed separately if repeated manual bumps become error-prone.

## Verification

Run a focused Python check that:

- parses both files with the standard `json` module;
- asserts `.claude-plugin/plugin.json` has top-level version `0.2.0`;
- asserts `.claude-plugin/marketplace.json` has plugin entry version `0.2.0`;
- asserts the two values match.

Run `git diff --check` and inspect the final diff to confirm that only the two intended JSON values changed. Existing repository CI remains the merge gate.

## Rollback

Before tagging, revert both fields to `0.1.0`. After publishing `v0.2.0`, corrections require a new patch release rather than moving the published tag.

## Non-Goals

- Creating or pushing `v0.2.0` within the preparation PR.
- Changing release or Docker-publish workflows.
- Automating version synchronization.
- Updating historical examples that intentionally reference `v0.1.0`.
- Changing web package version `0.0.0` or dependency versions.
